2️⃣对GitHub上词汇的理解

**Pull Request==** :开一个分支，把分支里面东西修改，发起请求接受修改，请求把这个分支合并回主分支main里面。

**Frok** ：在自己的GitHub账号创建一个项目一模一样的副本，主要用于你想要修改并参与这个开源项目。

**main** ：主分支包含新功能和所有新bug修复。

**branch分支** ：新的工作线（解决多人开发问题）

**realease** ：下载成品软件

**zip** ：下载源代码

**git clone** ：将完整的仓库下载到本地电脑，将全部：所有文件、所有历史修改记录、分支全都拷下来。

**fx/c ：用来修复bug的分支

**feat /** ：用来开发新功能分支

**docs/** ：用来改文档的分支

**trending** ：近期流行的趋向

**Repository** ：存放文件的文件夹README.md：仓库首页说明文档

## 三、是否有打不开GitHub经历？说说自己的判断。
有打不开GitHub经历😭

直接在浏览器搜索GitHub显示无法访问此页面

思考了思考一下 GitHub 的性质：

GitHub 服务器位于海外，没有在国内部署服务器与 CDN，数据需要跨海底光缆传输，距离很远；夜间属于网络高峰，线路拥挤、容易丢包，再加上 DNS 解析容易出错，就会一直转圈、超时，图片加载失败，访问时好时坏。
我尝试了这几种方案：

1. 将校园网切换为手机热点，更换网络通道；

2. 使用  Win + R  调出运行，打开  cmd ，执行  ping github.com ，拿到服务器 IP。修改 hosts 文件，建立域名与 IP 的静态映射，让电脑直接使用这个 IP，绕过容易出错的 DNS 解析，有机会连上。但这个 IP 会更新，而且跨境链路本身波动大，所以并不稳定；

3. 使用网络加速器优化线路。
 
结果： 这些办法都只能临时改善，偶尔可以连上一小段时间，没法一直稳定访问，过一会儿又会打不开。

## 五、这份文档凭什么称得上整洁规范？你遵循了哪些规范？

1. **层级标题清晰，结构有顺序**
使用 Markdown 的 `#`、`##`、`###` 分级标题，把内容分成五大块：Geek 理解、GitHub 认知、访问问题、主页美化、规范总结，从概念→词汇→踩坑实践→美化学习，逻辑由浅到深，阅读的人一眼就能看懂整体框架。

2. **内容分段，区分重点**
- 重要名词（Pull Request、Fork、main 等）用加粗标记；
- 知识点用数字序号、项目符号列表整理，不会大段文字堆在一起；
- 不同主题之间空一行，留白舒服，不会拥挤。

3. **格式统一，写法一致**
- 术语格式统一，分支命名、命令写法保持原样；
- 链接统一使用 `[文字](地址)` 标准 Markdown 链接格式；
- emoji 适量点缀，不滥用，只用来辅助区分板块，不打乱阅读；
- 代码、命令单独标出，和普通文字区分开。

4. **内容有条理，理论 + 实践结合**
不是单纯抄概念，既有学到的名词解释，也写了自己真实遇到的问题（GitHub 打不开）、自己尝试的解决办法、美化主页的实操经验，是**自己的学习记录**，不是杂乱摘抄。

5. **排版易读，兼顾 GitHub 渲染效果**
README /md 文件在 GitHub 网页上会自动渲染，我用的都是原生 Markdown 语法，没有奇怪的特殊格式，在 GitHub 打开不会乱码、排版错乱，电脑、手机浏览都能正常显示。
